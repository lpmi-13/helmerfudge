# Helmerfudge

A browser-only walkthrough of three related Helm update paths. Choose a path from the dropdown on the landing page to see its own trigger, steps, locations, and result. The default experience generates one fictional scenario shared by all three paths, so no files or credentials are needed.

The screens show one example workflow. Teams can place these steps elsewhere:

1. **Reusable chart update:** A commit to the reusable chart's Git source starts its CI. CI validates and packages the chart, then publishes a versioned chart to an OCI registry. This makes the version available to wrappers; it does not change an existing wrapper package or the cluster.
2. **Wrapper chart update:** A Git wrapper declares a versioned OCI reusable chart dependency. Wrapper CI fetches that version, packages it inside the wrapper chart, and publishes the versioned wrapper package to OCI. An Argo CD Application pinned to an older wrapper version keeps using that older version until its chart reference changes.
3. **Git values update:** A Git values change is reconciled by Argo CD in this example. Its repo-server fetches the already published wrapper package, merges the ordered Git values with chart defaults using Helm, and renders desired manifests. The application controller compares and syncs those manifests with the cluster. This path does not repackage either chart.

## Run locally

```bash
npm install
npm run dev
```

Open the URL printed by Vite (normally `http://127.0.0.1:5173`; Vite uses another local port if 5173 is occupied). The dev and preview servers bind only to `127.0.0.1`. Changes to the React and TypeScript source update in the browser through Vite.

Other checks:

```bash
npm run typecheck
npm test
npm run build
```

## Explore the story

- **Choose an update path** switches between the three screens and starts the selected path at its first step. **Play this path**, **Pause**, the arrow buttons, and the step trail support automatic or manual exploration.
- On the **wrapper chart** path, **Package** shows the wrapper `Chart.yaml` version line moving into the packaged copy, followed by the reusable chart `values.yaml` image tag line. Each destination updates when its source line arrives. The two YAML panels join into the completed package preview, which then settles into its graph node. The same YAML remains available by clicking the source and packaged-chart nodes.
- Drag empty canvas space to pan, use the zoom controls to inspect the graph, and click a node to open its details in a modal. Close it with the upper-right button, Escape, or a click outside the modal.
- On the **Git values** path, **Layer values** shows a later `image.tag` line overriding the chart default in the effective values. **Render** arcs `image.repository` and `image.tag` through their matching Helm expressions, then into the illustrative Deployment. **Argo CD sync** shows a representative rendered Deployment applied to a simulated cluster state. Use **Replay step** to repeat each YAML animation, choose an individual values file from the selector, or switch to **Flow map** to see the graph.
- **Regenerate** creates a fresh, seeded scenario with new fictional names in the form `word-xxxxxxxx` for charts, clusters, namespaces, resources, workers, queues, and registries, plus varied settings.
- **Use local files** opens the optional importer. Select a wrapper Helm `.tgz` with a dependency; select a separate dependency `.tgz` if the wrapper package does not contain it. You can add YAML values files and reorder them before import. The chart package parser supports standard Helm gzip/tar archives and imposes size limits.
- The **Manifests** node lets you inspect, copy, and download the illustrative manifest YAML.

The scenario models a wrapper chart, reusable dependency, and ordered GitOps values stack. It demonstrates Helm-style values layering (recursive maps, later scalar precedence, whole-list replacement, null removal) and worker defaults. Manifest output is **illustrative**; it is generated by the TypeScript model rather than the Helm template engine. Uploaded charts contribute dependency structure, numeric versions, and selected numeric settings, while their names, paths, and other string identifiers are replaced before display. SOPS encrypted values are shown as locked unless supplied in decrypted form. No files are uploaded to a server, and the app never connects to a cluster.

Packets move along the chart and values paths while result nodes appear at their destinations. Animation transitions use the `cubic-bezier(0.22, 1, 0.36, 1)` timing function. The interface honors reduced-motion preferences.
